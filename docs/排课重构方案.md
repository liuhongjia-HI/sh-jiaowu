# 排课管理重构方案

> 对标 Outlook 日历。客户已长期使用 Outlook 排课，交互与概念尽量与之对齐，不自创术语。

## 0. 概念澄清（重构的起点）

现在的 `ScheduleClass` 一条记录承载了两件事：**重复规则**（`DayOfWeek` + `StartDate`/`EndDate`）和**排课结果**。
客户的原话是对的 —— 它本质上只是一个排课结果，不是规则。问题在于这个"结果"被压缩成了一条记录，
于是「5 月 6 日那一节」在系统里根本不存在，拖它、改它、取消它，改的都是整学期。

重构后拆成两个实体：

| 实体 | 含义 | 说明 |
|---|---|---|
| `ScheduleLesson`（课次） | **一节课 = 一条记录**，有独立 ID、具体日期 | 排课结果的唯一载体。单次课也是它，`seriesId` 为空 |
| `ScheduleSeries`（重复规则） | 生成课次的模板 | 只有重复课才有。改它 = 批量重排未来课次 |

课次是第一公民。系列只是生成器，任何视图、考勤、课消、通知都挂课次，不挂系列。

## 1. 数据模型

### 1.1 系列身份（实现时简化：不建新表）

阶段一没有建 `schedule_series` 表。判断「哪些课次属于同一次提交」用课次上的 `series_id`
就够了；独立的系列记录只有在「修改重复规则本身并重新展开」时才有价值，那是后续迭代的事。
现阶段「整个系列」的语义是**批量改属性**（时间、老师、教室），改规则本身走「删了重排」——
Outlook 实际也是这么做的。这省掉了对 `memory.go` / `mysql_load` / `mysql_snapshot` 的一整轮改动。

下面是后续迭代要加规则编辑时的表结构预案：

#### `schedule_series`（后续迭代）

```
id                  VARCHAR(64) PK
course_id / teacher_id / campus_id / room_name / class_type
duration_minutes
freq                VARCHAR(16)   -- daily | weekly（monthly 预留，本期不实现）
interval_count      INT           -- 每 N 天 / 每 N 周，默认 1
by_day              VARCHAR(32)   -- weekly 时的星期集合，如 "1,3,5"
start_date / end_date
start_time / end_time
academic_year / semester          -- 按 start_date 落校历判定一次，不再漂移
created_by / created_at
```

`freq/interval_count/by_day/until` 是 RRULE 的子集。字段这样切是为了以后加 `monthly`
不用改表结构 —— 客户明确说按月和特殊日期后续迭代，但不能把 `interval` 写死成 1。

### 1.2 `schedule_lessons`（新表，取代现 `schedule_classes` 的主体地位）

```
id                  VARCHAR(64) PK
series_id           VARCHAR(64)   -- 空 = 单次课
lesson_date         DATE          -- 具体日期，不再是 day_of_week
start_time / end_time
course_id / course_name / subject / grade
teacher_id / teacher_name
campus_id / room_name / class_type / capacity
expected_student_count / reservation_note
academic_year / semester
detached            TINYINT       -- 1 = 已脱离系列，系列批量改动不再覆盖它
audit_status        VARCHAR(16)   -- 待确认 | 已确认 | 已驳回
audit_reason        TEXT          -- 驳回理由
audited_by / audited_at
fill_status         VARCHAR(16)   -- 待成班 | 已成班（人数维度，与审核无关）
status              VARCHAR(16)   -- 正常 | 已取消
override_note       TEXT          -- 越过软校验时的记录（越了谁的可上课时间）
created_by / created_by_role / created_at
```

`schedule_class_students` 改挂 `lesson_id`。

### 1.3 关键设计：`detached` 而不是"例外表"（已实现）

Outlook / Google Calendar 的做法是 **split-series**，不是 exception 表：

- 「仅此课次」→ 改这条 lesson，置 `detached = 1`，此后系列批量改动跳过它
- 「此课次及后续」→ 原系列 `end_date` 截断到前一节，**新建一个系列**承接后面的课次
- 「整个系列」→ 重排未来所有 `detached = 0` 且未上课的 lesson，**历史课次一律不动**

好处：不需要维护 exception 表和它的一致性；历史数据天然免疫；每条 lesson 都能独立查询，
月视图 / 考勤 / 课消直接读表，不用现算。

### 1.4 顺带修掉的两个存量问题

- `lesson_consumptions.schedule_class_id` 现在指向整个系列，说不清扣的是哪一节课的课时。
  改为指向 `lesson_id` 后，课消与课次一一对应。
- `MonthScheduleBoard` 里 `buildMonthDays(new Date())` 写死当前月且 `useMemo` 依赖为空
  —— 月视图翻不了月，是现网 bug，随视图重写一并修掉。

### 1.5 数据迁移

存量 `schedule_classes` 按 `day_of_week + start_date~end_date` 展开：
1. 每条生成一个 `schedule_series`（`freq=weekly, interval=1, by_day=原 day_of_week`）
2. 展开出全部 `schedule_lessons`，`audit_status` 一律置 `已确认`（存量数据视为已生效，不能让存量课在学生端集体消失）
3. `schedule_class_students` 按 lesson 复制
4. 迁移脚本必须可重跑（幂等），并保留 `schedule_classes` 表一个版本周期以便回滚

## 2. 权限与审核

### 2.1 规则（按客户确认）

| 操作人 | 建课结果 | 学生端可见 |
|---|---|---|
| 管理员（`ops_staff` / `campus_admin` / `super_admin`） | `audit_status = 已确认` | 立即可见 |
| 老师（`teacher`） | `audit_status = 待确认` | **不可见**，进管理员审核队列 |

管理员排课不需要跟老师确认；老师排课需要管理员确认。

### 2.2 必须拆开的两个状态（已实现，用词有调整）

**实现时的调整**：两个维度**不共用「确认」二字**。原方案里 `fill_status` 用「待成班/已成班」、
`audit_status` 用「待确认/已确认」，但「确认」在两处都出现会让谁都说不清。最终：

- `status`（沿用现有字段，不改值）= `待确认 / 已确认 / 已取消` —— **成班维度**：人数够不够、有没有被取消
- `auditStatus`（新增）= `待审核 / 已通过 / 已驳回` —— **审核维度**：管理员认不认

沿用 `status` 现有取值意味着既有前端筛选、列表、测试全部不受影响，改动面小得多。

原方案描述如下：


现在 `status` 的 `待确认/已确认` **不是审核**，是"人数够没够"：

```go
status := "待确认"
if len(students) >= minClassStudents(capacity) { status = "已确认" }
```

复用这个字段做审核会把两件事搅死。拆成：

- `fill_status`：`待成班 / 已成班` —— 沿用现有人数逻辑
- `audit_status`：`待确认 / 已确认 / 已驳回` —— 新增审核维度

### 2.3 学生端可见性收口（已实现）

统一收敛到一个谓词 `scheduleVisibleToStudent`（`已通过 && 非已取消`），出口共三处：

- `studentScheduleUnlocked` —— 学生课表
- `nextScheduleTodoClass` —— **实现时才发现的第二处泄露面**：学生首页「下一节课」待办，
  原本只过滤了已取消，待审核的课会从这里漏出去
- `canSeeScheduleClass` 的学生分支 —— 纵深防御，学生目前够不到那个接口
- 通知：待审核和已驳回的课在创建、修改、取消时都**不发**，审核通过时才发

小程序 `miniprogram/pages/schedule` 走的就是 `/student/schedule`，后端收口后无需改客户端。

**存量数据**：`backfillScheduleAuditStatus` 把升级前的课统一补为「已通过」。
漏掉这步的话，升级当天所有学生的课表会一起清空。

### 2.4 路由调整

`POST /schedule-classes` 等写接口现在只在 `registerOpsRoutes` 下（`routes.go:116-118`），
老师访问不到。需要开放给 `RoleTeacher`，并在 service 层按角色决定落哪个 `audit_status`。
新增管理员审核接口：

```
GET  /schedule-lessons/pending          审核队列
POST /schedule-lessons/:id/approve      通过
POST /schedule-lessons/:id/reject       驳回（必填理由）
```

老师的编辑权限：只能调整分配给自己的课程；处于「待审核」时可以继续修改，处于「已驳回」时修改即视为重新提交，清除旧审核结论并回到「待审核」。已通过的课要改，
一期沿用现有提示「请联系教务调整课程」，不做变更申请流。服务端必须校验请求里的 `teacherId` 等于当前教师 ID，不能把前端下拉框限制当作权限边界。

## 3. 冲突校验分级

客户要求「学生撞课当场拦截」，其余按最佳实践定。原则是：
**物理上不可能的事硬拦截，只是"不太方便"的事软提醒**。因为客户明确说了
管理员可能线下已经跟老师和学生沟通好时间，可上课时间只是参考范围，不是铁律。

| 校验项 | 级别 | 理由 |
|---|---|---|
| 学生撞课 | 🔴 硬拦截 | 客户明确要求；一个人不能同时在两节课 |
| 老师撞课 | 🔴 硬拦截 | 同上，物理不可能 |
| 教室撞课（填了教室时） | ⚪ 不校验 | **实现时修正**：代码里「教室只登记、不阻塞排课」是既有的产品决策（见 TestScheduleClassKeepsRoomMetadataWithoutBlocking），不擅自推翻，需客户确认是否要改 |
| 学生年级与课程不符 | 🔴 硬拦截 | 现有业务规则，保留 |
| 学生未开通该学科 | 🔴 硬拦截 | 现有业务规则，保留 |
| 超班型容量 | 🔴 硬拦截 | 现有业务规则，保留 |
| **超出老师可上课时间** | 🟡 **软提醒** | 线下可另行沟通；**这是从现在的硬拦截降级** |
| **超出学生可上课时间** | 🟡 **软提醒** | 同上 |
| 落在节假日 / 寒暑假 | ⚪ 不校验 | 客户明确：交给排课人自己管 |

### 落地要求

1. `teacherAvailable` / `studentAvailable` 两处从 `return error` 改为收集 warning
   （`memory_scheduling.go:383-390`）。
2. 接口返回 `{ conflicts: [...], warnings: [...] }`。有 `conflicts` 直接 4xx；
   只有 `warnings` 时前端弹二次确认，用户确认后带 `ignoreWarnings: true` 重提。
3. **override 必须留痕**：写入 `override_note` + 操作日志（谁、什么时候、越了谁的时间）。
   这是把硬拦截降级为软提醒的前提 —— 出了问题要能追溯。
4. 老师建课时，软提醒同样是软提醒，但**越界标记要带到审核界面**，让管理员一眼看到
   "这节课越过了张老师的可上课时间"。
5. 「可上课时间」的定位随之明确：**匹配与监管的参考范围，不是排课的硬约束**。
   候选时段推荐仍然只在可上课时间内匹配（这是它的价值），但手工排课可以越界。

## 4. 重复规则

- 本期：`daily`（每 N 天）、`weekly`（每 N 周 + 星期集合）
- 结束方式：`按日期结束（until）` / `按次数结束（count）`，两者择一
- 不跳节假日、不跳寒暑假（客户明确）
- 生成上限：单次生成课次数量设硬上限（建议 200），超限拒绝并提示缩短周期。
  按日重复 + 长跨度很容易一口气生成上千条，必须有闸

`monthly` 与特殊日期按客户要求本期不做，但字段结构已预留。

## 5. 视图规范（对标 Outlook）

| 视图 | 要求 | 状态 |
|---|---|---|
| **日视图** | 穿透查看单日详情；显示不全时弹小窗列出全部课程 | ✅ 与周视图共用同一套溢出折叠：折叠块点开是 Popover 完整列表，可直接进入任意一节 |
| **周视图** | 核心排课场景；拖拽调时间；**单格最多 3 个课时，超限折叠为加号** | ✅ `weekCellMaxLessons = 3`。三节以内全部显示；超过三节时前两节正常显示、第三格变 `+N`，保证「最多三个」是字面意义的三个可视块 |
| **月视图** | 展示当月所有课次的**开始时间 / 教师姓名 / 年级 / 科目 / 学生姓名** | ✅ 已补学生姓名（超长省略，完整名单在详情里）；翻月 bug 已修 |

日视图泳道**不套用 3 的上限**：那里一列就是一个老师，同时段重叠本身就是排课错误，
数量极少，按列宽推算更合适。上限做成了 `layoutOverlappingItems` 的可选参数，两种语义各走各的。

### 候选排课已下线

原「查找可排时间 → 可排方案 → 确认成班」这条链路已按客户要求整体移除，
改为直接在日/周/月视图上操作（双击空白格新建、拖拽调时间、右键复制）。
连带删除：候选查找表单、可排方案卡、协调建议卡、确认成班抽屉、视图里的候选叠加层，
以及 `CandidatePanel.tsx` 整个文件，前端净减约 230 行。

后端 `POST /scheduling/candidates` 及其匹配算法**保留但已无调用方** ——
匹配能力本身可能换个形式用回来（比如新建时提示「这个时段谁有空」），
是否彻底删除待定。

### 拖拽行为（依赖第 1 节）

拖动重复课次时弹出三选一：**仅此课次 / 此课次及后续 / 整个系列**（客户确认需要）。
单次课不弹，直接改。这是修复"拖一节课挪走整学期"这个现网 bug 的正解。

### 右键快捷排课（已实现）

**实现方式与原设想不同**：没有做「复制 → 粘贴到目标格」的两步剪贴板流程，而是
右键 →「复制这节课」→ 直接打开新建表单并预填原课的课程、老师、学生、班型、时段，
用户改个时间就能提交。少一步操作，也不需要维护「剪贴板里有什么」这个隐藏状态。

三处都挂了右键菜单（复制 / 调整）：周视图、日视图泳道、月视图。

两条已由测试锁住（`TestCopiedLessonStillRunsConflictChecks`、`TestTeacherCopiedLessonStillNeedsReview`）：
1. 复制走的是普通建课接口，**照常跑全套冲突校验** —— 源课合法不代表新时间合法
2. 复制出来的是独立单次课（不带 `seriesId`、不继承审核状态），老师复制出的课仍须审核，
   否则复制就成了绕过审核的后门

## 6. 科目颜色元数据（已实现）

**客户已确认学科清单**：就是 Outlook 里那 8 个分类，需求文案写的「10 门」不准确。

| 学科（系统字典值） | 短标签 | 主色 | 文字/底色对比度 |
|---|---|---|---|
| 英文 | Eng | `#1A6FD4` | 10.91 ✓ AA |
| 数学 | Math | `#E8C400` | 6.56 ✓ AA |
| 地理 | Geo | `#3A9BBF` | 9.07 ✓ AA |
| 科学 | Sci | `#1B3FA8` | 13.30 ✓ AA |
| 综合科学 | Sci | `#1B3FA8` | 同上 |
| 语文 | CHN | `#A855D8` | 10.29 ✓ AA |
| 历史 | His | `#8B5A2B` | 11.64 ✓ AA |
| 化学 | Chem | `#E8730C` | 8.88 ✓ AA |
| 物理 | Phy | `#C2185B` | 11.57 ✓ AA |

注意系统字典用的是**「英文」**不是「英语」；「英语」作为历史数据别名映射到同一门。

**「综合科学」与「科学」共用 Sci 的颜色**：综合科学现仅用于兼容旧课程数据，
新课程矩阵 G1-G12 统一使用科学；保留旧颜色映射可以保证历史课表仍正常显示。

### 存放位置：系统设置，不是前端常量

后端 `defaultSubjectColors()` 写进 settings 的 `subjectColors` 键（JSON），
沿用 `academicCalendar` 同一套机制，没有新开接口。运营改色不用发版。

前端 `web/src/utils/subject-colors.ts` 是**唯一来源**，登录后从 `/settings` 拉一次。
内置默认值与后端一致，所以设置还没拉回来时不会先闪一版旧色再跳色；设置值写坏了
（JSON 解析失败、色值非法）就保持默认，一个手滑的设置项不该让整个课表变灰。

### 顺带修掉的不一致

在这之前**存在两套独立的调色板**：`SchedulingViews.subjectColor`（排课页）和
`resource-shared.subjectColor`（资源页），同一门课在两处是不同颜色——比如「英文」
排课页是蓝色、资源页是绿色。现在两边共用同一个来源。

排课页原来的分组也和客户不符：地理+历史合一色、科学/物理/化学合一色，
而客户那边这五门各有独立颜色。

### 只让运营挑一个颜色

课程块需要底色/边框/主色/文字色四个值，但元数据里只存一个主色，
其余按固定比例推导（底色 = 88% 白 + 12% 主色；文字 = 主色压暗 55%）。
运营不用理解四者关系。推导结果已逐一校验对比度，8 门全部达到 WCAG AA
（最差是数学的黄色 6.56）——黄色这类高亮主色直接当文字色会完全看不见，
所以压暗是必须的，不是可选优化。

**例外**：「老师可授课」「学生可上课」不是学科，是可上课时间底纹用的伪类目，
单独在 `SchedulingViews` 里给色，不进学科元数据——否则运营会在配色表里
看到两条没法解释的条目。

## 9. 对标 Outlook 的补齐（第二轮）

客户明确：**只管排课功能本身**，打印、共享、拆分视图不做；
**能排课的学生都是付费的**，所以不需要付费/试听标记字段。

| 项 | 说明 |
|---|---|
| **时间轴自适应** ✅ | `buildTimelineRange` 原本是空壳（`void items` + 固定 08:00-22:00），22:00 之后开始的课算出的 top 超过画布高度、直接渲染到列外面，用户看不到。改为**默认窗口 ∪ 实际内容**单向外扩：不能改成「紧贴内容」，因为时间轴同时是拖拽落点，收紧后就没法把课往更早时间挪 |
| **月视图压成单行** ✅ | 原本是四行 grid（时间/科目年级/教师/学生各一行），一条占 4 行高、一格连两条都放不下。改为单行「时间 · 教师 年级 科目短标签 · 学生」，超宽省略、完整内容挂 title。**这才是月视图放不下几节课的根因，光加折叠不压排版等于把阈值设成 1** |
| **学科短标签用上** ✅ | 元数据里的 `Eng/Math/Geo/Sci/CHN/His/Chem/Phy` 之前只存着没用，视图仍在显示全名。客户能把一节课塞进一行靠的就是短标签 |
| **月视图溢出折叠** ✅ | `monthCellMaxLessons = 4`，与客户截图密度一致（4 条 + `+2`）。超出时列前 3 条 + `+N`，点开是当天完整列表 |
| **重复课次标记** ✅ | 客户截图里每个重复课次右下角都有回环图标。这不只是好看：拖动重复课次会弹三选一，用户事先必须能看出哪节是重复课。已脱离系列的课次（`detached`）用断开的图标区分——它拖动时不会问范围，标记必须诚实反映 |
| **拉伸改时长** ✅ | 拖块下沿改结束时间。用 pointer 事件而非 HTML5 drag（后者是「挪到别处」的语义，且和块的 `draggable` 抢事件），`setPointerCapture` 保证划出块外仍跟手；**只在松手时回调一次**，否则一次拉伸会变成十几次写库。拉伸走同一条调课链路，所以重复课次同样要问范围——`TestResizeRepeatingLessonRespectsScope` 锁住了这一点，少了它拉伸就是绕过三选一的后门 |
| **工作周视图** ✅ | 新增「工作周」（周一至周五），复用周视图的时间轴。**周视图仍然是完整 7 天，没有改窄**——校外教培周六日恰恰是排课高峰，把周末从默认视图里砍掉是把最该看的两天藏起来 |

### 事件命名约定（已改为客户约定）

标题从 `英文 1V1 小班` 改为 **`教师 年级 科目 学生`**，对照客户 Outlook 里的
`Clara G5 Eng Zoe&Arthur`。示例：`英语老师 G5 Eng 小明`。

改的理由不只是「客户这么用」：课表上一眼要认的是「谁的课、几年级、什么科」，
原来把**班型**放在标题最前面，而班型在课程块上本来就有独立标签，不需要再占标题开头。

组成部分：
- 年级用 `G1`–`G9` 记号（`gradeCode`），认不出的年级原样保留——
  标题里出现一个陌生年级，比出现一段空白更容易被发现和纠正
- 学科用元数据里的短标签（`Eng`/`Math`/…），设置查不到时退回学科全名
- 学生还没定（预留时段）就只拼到科目，不留空占位

### 标题实时派生，不做数据回填

后端 `Name` 仍然存一份，但**日历上显示的标题改为前端实时派生**
（`scheduleLessonTitle`，日/周/月三个视图共用）。

这样处理有两个好处：存量课次立刻显示为新格式，不需要写一个跨四张表 join 的回填脚本；
更重要的是根治了staleness——标题是派生数据，存下来就会过时，老师改个名、
班里加个学生，存的那份就和实际对不上了。后端存的那份定位为**操作日志和通知的历史快照**，
两者用途不同，各自成立。

### 工作周牵出的两处写死

- `.schedule-timeline-grid` 的 `grid-template-columns` 原本是 `repeat(7, ...)`，
  5 列时会多出两条空列；改成 `repeat(var(--day-count), ...)`，天数由组件传入。
  `min-width` 同样跟着列数算，否则 5 列会被 980px 的下限压窄。
  `.month-board`（月历）和 `.schedule-mini-calendar`（迷你日历）保持 7 列不变。
- 迷你日历的整周高亮原本覆盖 7 天：工作周下点周六会跳到那一周，但周六列
  根本不显示，高亮却把它点亮了。`weekDayCount` 让高亮只覆盖实际显示的天数。
