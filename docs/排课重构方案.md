# 排课管理重构方案

> 对标 Outlook 日历。客户已长期使用 Outlook 排课，交互与概念尽量与之对齐，不自创术语。

## 0. 概念澄清（重构的起点）

现在的 `ScheduleClass` 一条记录承载了两件事：**重复规则**（`DayOfWeek` + `StartDate`/`EndDate`）和**排课结果**。
客户的原话是对的 —— 它本质上只是一个排课结果，不是规则。问题在于这个"结果"被压缩成了一条记录，
于是「5 月 6 日那一节」在系统里根本不存在，拖它、改它、取消它，改的都是整学期。

重构后拆成两个实体：

| 实体 | 含义 | 说明 |
|---|---|---|
| `ScheduleLesson`（课次） | **一节课 = 一条记录**，有独立 ID、具体日期 | 排课结果的唯一载体。单次课也是它，`seriesId` 为空 |
| `ScheduleSeries`（重复规则） | 生成课次的模板 | 只有重复课才有。改它 = 批量重排未来课次 |

课次是第一公民。系列只是生成器，任何视图、考勤、课消、通知都挂课次，不挂系列。

## 1. 数据模型

### 1.1 系列身份（实现时简化：不建新表）

阶段一没有建 `schedule_series` 表。判断「哪些课次属于同一次提交」用课次上的 `series_id`
就够了；独立的系列记录只有在「修改重复规则本身并重新展开」时才有价值，那是后续迭代的事。
现阶段「整个系列」的语义是**批量改属性**（时间、老师、教室），改规则本身走「删了重排」——
Outlook 实际也是这么做的。这省掉了对 `memory.go` / `mysql_load` / `mysql_snapshot` 的一整轮改动。

下面是后续迭代要加规则编辑时的表结构预案：

#### `schedule_series`（后续迭代）

```
id                  VARCHAR(64) PK
course_id / teacher_id / campus_id / room_name / class_type
duration_minutes
freq                VARCHAR(16)   -- daily | weekly（monthly 预留，本期不实现）
interval_count      INT           -- 每 N 天 / 每 N 周，默认 1
by_day              VARCHAR(32)   -- weekly 时的星期集合，如 "1,3,5"
start_date / end_date
start_time / end_time
academic_year / semester          -- 按 start_date 落校历判定一次，不再漂移
created_by / created_at
```

`freq/interval_count/by_day/until` 是 RRULE 的子集。字段这样切是为了以后加 `monthly`
不用改表结构 —— 客户明确说按月和特殊日期后续迭代，但不能把 `interval` 写死成 1。

### 1.2 `schedule_lessons`（新表，取代现 `schedule_classes` 的主体地位）

```
id                  VARCHAR(64) PK
series_id           VARCHAR(64)   -- 空 = 单次课
lesson_date         DATE          -- 具体日期，不再是 day_of_week
start_time / end_time
course_id / course_name / subject / grade
teacher_id / teacher_name
campus_id / room_name / class_type / capacity
expected_student_count / reservation_note
academic_year / semester
detached            TINYINT       -- 1 = 已脱离系列，系列批量改动不再覆盖它
audit_status        VARCHAR(16)   -- 待确认 | 已确认 | 已驳回
audit_reason        TEXT          -- 驳回理由
audited_by / audited_at
fill_status         VARCHAR(16)   -- 待成班 | 已成班（人数维度，与审核无关）
status              VARCHAR(16)   -- 正常 | 已取消
override_note       TEXT          -- 越过软校验时的记录（越了谁的可上课时间）
created_by / created_by_role / created_at
```

`schedule_class_students` 改挂 `lesson_id`。

### 1.3 关键设计：`detached` 而不是"例外表"（已实现）

Outlook / Google Calendar 的做法是 **split-series**，不是 exception 表：

- 「仅此课次」→ 改这条 lesson，置 `detached = 1`，此后系列批量改动跳过它
- 「此课次及后续」→ 原系列 `end_date` 截断到前一节，**新建一个系列**承接后面的课次
- 「整个系列」→ 重排未来所有 `detached = 0` 且未上课的 lesson，**历史课次一律不动**

好处：不需要维护 exception 表和它的一致性；历史数据天然免疫；每条 lesson 都能独立查询，
月视图 / 考勤 / 课消直接读表，不用现算。

### 1.4 顺带修掉的两个存量问题

- `lesson_consumptions.schedule_class_id` 现在指向整个系列，说不清扣的是哪一节课的课时。
  改为指向 `lesson_id` 后，课消与课次一一对应。
- `MonthScheduleBoard` 里 `buildMonthDays(new Date())` 写死当前月且 `useMemo` 依赖为空
  —— 月视图翻不了月，是现网 bug，随视图重写一并修掉。

### 1.5 数据迁移

存量 `schedule_classes` 按 `day_of_week + start_date~end_date` 展开：
1. 每条生成一个 `schedule_series`（`freq=weekly, interval=1, by_day=原 day_of_week`）
2. 展开出全部 `schedule_lessons`，`audit_status` 一律置 `已确认`（存量数据视为已生效，不能让存量课在学生端集体消失）
3. `schedule_class_students` 按 lesson 复制
4. 迁移脚本必须可重跑（幂等），并保留 `schedule_classes` 表一个版本周期以便回滚

## 2. 权限与审核

### 2.1 规则（按客户确认）

| 操作人 | 建课结果 | 学生端可见 |
|---|---|---|
| 管理员（`ops_staff` / `campus_admin` / `super_admin`） | `audit_status = 已确认` | 立即可见 |
| 老师（`teacher`） | `audit_status = 待确认` | **不可见**，进管理员审核队列 |

管理员排课不需要跟老师确认；老师排课需要管理员确认。

### 2.2 必须拆开的两个状态（已实现，用词有调整）

**实现时的调整**：两个维度**不共用「确认」二字**。原方案里 `fill_status` 用「待成班/已成班」、
`audit_status` 用「待确认/已确认」，但「确认」在两处都出现会让谁都说不清。最终：

- `status`（沿用现有字段，不改值）= `待确认 / 已确认 / 已取消` —— **成班维度**：人数够不够、有没有被取消
- `auditStatus`（新增）= `待审核 / 已通过 / 已驳回` —— **审核维度**：管理员认不认

沿用 `status` 现有取值意味着既有前端筛选、列表、测试全部不受影响，改动面小得多。

原方案描述如下：


现在 `status` 的 `待确认/已确认` **不是审核**，是"人数够没够"：

```go
status := "待确认"
if len(students) >= minClassStudents(capacity) { status = "已确认" }
```

复用这个字段做审核会把两件事搅死。拆成：

- `fill_status`：`待成班 / 已成班` —— 沿用现有人数逻辑
- `audit_status`：`待确认 / 已确认 / 已驳回` —— 新增审核维度

### 2.3 学生端可见性收口（已实现）

统一收敛到一个谓词 `scheduleVisibleToStudent`（`已通过 && 非已取消`），出口共三处：

- `studentScheduleUnlocked` —— 学生课表
- `nextScheduleTodoClass` —— **实现时才发现的第二处泄露面**：学生首页「下一节课」待办，
  原本只过滤了已取消，待审核的课会从这里漏出去
- `canSeeScheduleClass` 的学生分支 —— 纵深防御，学生目前够不到那个接口
- 通知：待审核的课**不发**，审核通过时才发

小程序 `miniprogram/pages/schedule` 走的就是 `/student/schedule`，后端收口后无需改客户端。

**存量数据**：`backfillScheduleAuditStatus` 把升级前的课统一补为「已通过」。
漏掉这步的话，升级当天所有学生的课表会一起清空。

### 2.4 路由调整

`POST /schedule-classes` 等写接口现在只在 `registerOpsRoutes` 下（`routes.go:116-118`），
老师访问不到。需要开放给 `RoleTeacher`，并在 service 层按角色决定落哪个 `audit_status`。
新增管理员审核接口：

```
GET  /schedule-lessons/pending          审核队列
POST /schedule-lessons/:id/approve      通过
POST /schedule-lessons/:id/reject       驳回（必填理由）
```

老师的编辑权限：**只能改自己创建且仍处于「待确认」的课次**。已通过的课要改，
一期先沿用现有提示「请联系教务调整课程」，不做变更申请流（避免一期铺太开）。

## 3. 冲突校验分级

客户要求「学生撞课当场拦截」，其余按最佳实践定。原则是：
**物理上不可能的事硬拦截，只是"不太方便"的事软提醒**。因为客户明确说了
管理员可能线下已经跟老师和学生沟通好时间，可上课时间只是参考范围，不是铁律。

| 校验项 | 级别 | 理由 |
|---|---|---|
| 学生撞课 | 🔴 硬拦截 | 客户明确要求；一个人不能同时在两节课 |
| 老师撞课 | 🔴 硬拦截 | 同上，物理不可能 |
| 教室撞课（填了教室时） | ⚪ 不校验 | **实现时修正**：代码里「教室只登记、不阻塞排课」是既有的产品决策（见 TestScheduleClassKeepsRoomMetadataWithoutBlocking），不擅自推翻，需客户确认是否要改 |
| 学生年级与课程不符 | 🔴 硬拦截 | 现有业务规则，保留 |
| 学生未开通该学科 | 🔴 硬拦截 | 现有业务规则，保留 |
| 超班型容量 | 🔴 硬拦截 | 现有业务规则，保留 |
| **超出老师可上课时间** | 🟡 **软提醒** | 线下可另行沟通；**这是从现在的硬拦截降级** |
| **超出学生可上课时间** | 🟡 **软提醒** | 同上 |
| 落在节假日 / 寒暑假 | ⚪ 不校验 | 客户明确：交给排课人自己管 |

### 落地要求

1. `teacherAvailable` / `studentAvailable` 两处从 `return error` 改为收集 warning
   （`memory_scheduling.go:383-390`）。
2. 接口返回 `{ conflicts: [...], warnings: [...] }`。有 `conflicts` 直接 4xx；
   只有 `warnings` 时前端弹二次确认，用户确认后带 `ignoreWarnings: true` 重提。
3. **override 必须留痕**：写入 `override_note` + 操作日志（谁、什么时候、越了谁的时间）。
   这是把硬拦截降级为软提醒的前提 —— 出了问题要能追溯。
4. 老师建课时，软提醒同样是软提醒，但**越界标记要带到审核界面**，让管理员一眼看到
   "这节课越过了张老师的可上课时间"。
5. 「可上课时间」的定位随之明确：**匹配与监管的参考范围，不是排课的硬约束**。
   候选时段推荐仍然只在可上课时间内匹配（这是它的价值），但手工排课可以越界。

## 4. 重复规则

- 本期：`daily`（每 N 天）、`weekly`（每 N 周 + 星期集合）
- 结束方式：`按日期结束（until）` / `按次数结束（count）`，两者择一
- 不跳节假日、不跳寒暑假（客户明确）
- 生成上限：单次生成课次数量设硬上限（建议 200），超限拒绝并提示缩短周期。
  按日重复 + 长跨度很容易一口气生成上千条，必须有闸

`monthly` 与特殊日期按客户要求本期不做，但字段结构已预留。

## 5. 视图规范（对标 Outlook）

| 视图 | 要求 | 现状 |
|---|---|---|
| **日视图** | 穿透查看单日详情；显示不全时弹小窗列出全部课程 | 现为老师泳道视图，**无溢出折叠** → 待做 |
| **周视图** | 核心排课场景；拖拽调时间；**单格最多 3 个课时，超限折叠为加号** | 现为等宽分列、不限个数 → 待做 |
| **月视图** | 展示当月所有课次的**开始时间 / 教师姓名 / 年级 / 科目 / 学生姓名** | 现缺学生姓名，且**翻不了月** → 待做 |

### 拖拽行为（依赖第 1 节）

拖动重复课次时弹出三选一：**仅此课次 / 此课次及后续 / 整个系列**（客户确认需要）。
单次课不弹，直接改。这是修复"拖一节课挪走整学期"这个现网 bug 的正解。

### 右键快捷排课

右键课次 → 复制 → 粘贴到目标时间格，生成新课次，仅需改时间与部分属性。
两个要点：
1. **复制出的课必须重跑全套校验** —— 源课合法不代表新时间合法
2. 老师复制出来的课同样落 `待确认`

周视图和月视图都要挂右键菜单。

## 6. 科目颜色元数据

客户提供的 Outlook 分类是 8 个：Eng / Math / Geo / Sci / CHN / His / Chem / Phy。
系统内 `ALL_SUBJECTS` 是 9 门（`web/src/utils/curriculum.ts:11`），多出「综合科学」
（与「科学」是两个不同学科，不能合并）。客户需求文案写的是 10 门 —— **数字对不上，需确认**。

### 做成后端元数据，不做前端常量

新增 `subject_metadata` 表 / 配置：

```
subject       VARCHAR(32) PK   -- 业务字典值，如 "综合科学"
short_label   VARCHAR(16)      -- 日历上的短标签，如 "Sci+"
color_token   VARCHAR(16)      -- 十六进制色值
sort_order    INT
enabled       TINYINT
```

理由：颜色和学科清单是运营会调的东西，放前端常量意味着每次调整都要发版。
接口挂在现有 `GET /settings` 体系下，前端启动时拉一次。
