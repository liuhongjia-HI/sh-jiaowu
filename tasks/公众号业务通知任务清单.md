# 公众号业务通知任务清单

日期：2026-10-01。依据：用户已接受的公众号业务通知方案及提供的五个模板详情。

本清单是实施与验收计划，复选框按实际实现和验收证据更新。首期交付三类课程通知，作业通知分后续阶段接入。

## 1. 范围与固定规则

| 场景 | 模板编号 | 实际字段 | 首期状态 |
| --- | --- | --- | --- |
| 排课首次正式确认 | 69982 | 课程 `thing1`、学生 `thing2`、时间 `time4` | 纳入首期 |
| 已确认课程调课生效 | 55227 | 课程 `thing12`、调前 `time2`、调后 `time4`、学生 `thing7` | 纳入首期 |
| 课前提醒 | 52442 | 课程 `thing1`、时间 `time2`、学生 `thing14` | 纳入首期；截图场景说明为“上课提醒” |
| 作业提交成功 | 50738 | 课程 `thing6`、作业 `thing2`、提交时间 `time4` | 后续接入，默认关闭 |
| 作业批改异常 | 65417 | 作业 `thing7`、班级 `thing5`、原因 `const2` | 后续接入，依赖异常流程与审核枚举 |

模板编号仅用于人工识别，发送使用公众号同步返回的实际 `template_id`，不能用编号代替。

- 排课通知仅在业务保存成功、审核通过且正式确认后产生。调课比较上次已生效安排与本次已生效安排，保留变更前后快照。
- 同次操作、同一课程系列、同一学生、同一公众号 OpenID 合并一条；卡片展示首次受影响课次，详情列出全部课次。不同孩子、不同课程系列保留各自通知。
- 课前提醒默认提前 2 小时，普通提醒发送窗口为 `Asia/Shanghai` 的 08:00—21:00；窗口外的计划提醒提前到上一日 20:00。
- 确认或调课通知已在开课前 2 小时内被微信受理时，不再紧接着发送该安排版本的课前提醒。不可触达、发送失败不视为已提醒。
- 调课、取消、驳回及权限关系变化后，旧任务必须重新核验；已被替代或过期的任务失效。
- 首次启用不补发历史确认和历史调课；只接收启用后的业务事件，并安排未来有效课次的课前提醒。
- 当前缺少匹配模板的课程取消、作业发布、批改完成，保留学生可见的站内通知，不套用其他模板。
- API 沿用 `/api`、`{ code, message, data }` 和现有认证权限；管理端操作人沿用 `X-Operator-ID`、`X-Operator-Name`。

## 2. 首期任务

### T01：定义业务事件、模板绑定和发送状态（依赖：无）

- [x] 定义首次确认、调课生效、课前提醒三个事件及业务关联字段；包含事件 ID、操作批次、课程系列、课次、学生、变更版本与前后快照。
- [x] 定义业务类型到实际模板 ID 的配置，事件开关及启用时间；模板标题用于展示，路由不依赖标题字符串。
- [x] 区分待发送、发送中、微信已受理、已送达、发送失败、配置错误、不可触达、结果待确认、已失效；送达不等于已读。
- [x] 确定字段契约与有效期：`thing` 最多 20 字符，`const` 使用审核枚举，时间按微信允许格式处理；课程长名称使用可辨识简称。

验收：契约能表达真实的二次调课、批量操作、任务失效、回执和多孩子收件人；更新 Go 类型、管理端类型及 `docs/API.md`。

### T02：持久化事件、发送任务与配置（依赖：T01）

- [x] 沿用现有 MySQL 升级、加载、增量写入模式，增加必要的事件、任务、模板绑定数据；保留现有通知记录。
- [x] 业务事件、站内通知和公众号任务与业务变更在同一事务中提交；事务回滚不发送微信消息。
- [x] 在数据库层保护事件幂等和接收任务唯一性；任务保存字段快照、`due_at`、`expires_at`、重试次数、下次重试时间、微信 `msgid`、防重标识和失败原因。
- [x] 增加任务领取与超时恢复机制，防止后台任务并发或进程重启造成重复消费；无需引入新消息中间件。

验收：模拟业务回滚、并发重复请求、进程重启，事件和任务不丢失，不重复创建；已有业务数据及通知历史可正常读取。

### T03：统一家长身份匹配与接收范围（依赖：T01、T02）

- [x] 按学生 ID 查有效家长关系，过滤停用学生、停用家长、失效关系及未关注用户，再通过 UnionID 匹配公众号 OpenID。
- [x] 自动通知不再靠学生姓名或学生档案中的单一公众号 OpenID 选择接收人；同一事件、学生和 OpenID 去重。
- [x] 小程序微信登录补齐家长 UnionID；公众号关注回调异步拉取用户资料，补齐 UnionID，取消关注立即更新可触达状态。
- [x] 提供定期关注者同步和可触达统计；发送前重新核验关系，新增关注不自动追发已过期通知。

验收：一学生多家长、一家长多孩子、同名学生、解绑、取消关注、UnionID 缺失均得到正确结果；无越权收件人。

### T04：统一模板发送接口与回执（依赖：T01、T02）

- [x] 自动通知与现有手动通知复用同一底层微信发送实现，支持实际模板 ID、动态字段、受控小程序跳转和 `client_msg_id`。
- [x] 复用或补齐公众号 access token 缓存与失效刷新，避免逐条消息反复申请 token；不记录凭据。
- [x] 保存微信返回的 `msgid`，接入模板消息发送结果回调，校验签名或解密，支持重复回调及回调先于本地结果落库的情况。
- [x] 按微信字段类型验证内容，准确区分模板/枚举/字段错误、取消关注、暂时错误和结果不确定。

验收：固定模拟响应验证受理、回执成功、回执失败及错误分类；发送结果不再把接口受理直接当成送达。

### T05：后台发送、重试与失效处理（依赖：T02、T03、T04）

- [x] 增加随 API 生命周期启动和停止的后台任务，按计划时间领取持久化任务；外部发送在业务锁与事务之外执行。
- [x] 临时失败按 1、5、15 分钟间隔最多重试 3 次，均受有效期约束；身份和配置错误停止自动重试。
- [x] 请求结果不确定时使用相同防重标识；微信防重窗口为 10 分钟，超出窗口不盲目自动重发，保留“结果待确认”。
- [x] 发送及人工补发前重新核验业务版本、课程状态、接收权限和有效期；已受理/已送达、失效任务禁止普通补发。
- [x] 处理重启恢复、领取超时、停用开关及旧链路遗留的“发送中”记录，避免新旧发送器同时处理同一业务。

验收：网络超时、限流、重启及多消费者场景均不要求用户重新提交业务；不能声称跨微信防重窗口保证绝对只发送一次。

### T06：接入首次确认与调课生效事件（依赖：T01、T02、T03）

- [x] 在首次正式确认或首次审核通过时产生确认事件；重复保存、重复审核请求不重复产生。
- [x] 保留上次已生效安排；调课经过审核时，以最终通过安排与该快照比较，而非与最后一次草稿比较。
- [x] 日期、开始或结束时间变化产生调课事件；无时间变化或内部备注变化不套用调课模板。
- [x] 拒绝和取消不产生确认消息；取消以及所有使课程不再有效的动作使旧提醒失效。

验收：草稿改三次后审核只发最终结果；周一→周二→周三产生两次独立调课；保存失败不发。

### T07：系列操作合并与通知详情快照（依赖：T06）

- [x] 同一批次、课程系列、学生和 OpenID 合并确认/调课通知；仅收集该学生实际受影响的有效课次。
- [x] 卡片使用首次受影响课次的真实字段，详情列出所有课次及前后时间；不在时间字段中填“共 16 节”等描述。
- [x] 不同孩子和不同课程系列不合并；逐次真实变更不因历史通知存在而被拦截。

验收：一次确认 16 次课不逐课刷屏；“此课次”“此课次及后续”“整个系列”的受影响范围与通知详情一致。

### T08：课前提醒计划与临近开课去重（依赖：T05、T06、T07）

- [x] 为未来有效课次按时间版本创建提醒，按 2 小时与 08:00—21:00 窗口规则计算；发送前再检查课程和接收关系。
- [x] 调课重新安排新版本任务，取消使旧任务失效；旧时间下的发送结果不能抑制新时间下的提醒。
- [x] 在 2 小时内已受理的确认/调课通知抑制同版本提醒；失败或结果不确定时依据发送状态处理，避免两路同时补发。
- [x] 临近开课才创建课程时，优先处理确认消息，不补发已经错过的前一日提醒；业务提醒到开课时间即失效。

验收：覆盖普通课、早课、晚课、临近开课确认、二次调课、取消及停机恢复；一份有效安排最多有一项普通课前提醒任务。

### T09：学生站内通知与安全详情 API（依赖：T02、T03、T07）

1. **基础能力：** T01 → T02 → T03/T04 → T05。
2. **课程业务：** T06 → T07 → T08；完成 T07 后接 T09 → T10，按依赖接 T11。
